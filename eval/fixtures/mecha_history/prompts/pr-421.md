# The document cache leaks which files the owner read, and prune can report a false clean

**Crate:** `mecha-core` (`src/document.rs`, the `Cache` type)

## What is wrong

The document cache keeps one entry per PDF under its root, and each entry's directory is named by the file's sha256. Today only the entry directory a write lands in is tightened, and if that chmod fails nobody hears about it. The cache root and any directories between the root and the file stay at whatever the umask gave them. If the root already exists at `0775` or `0755`, any local user can list it and check whether the owner opened a particular document by hashing their own copy.

The files are not protected either. Stored layers and OCR pages (the document's text) are written with a plain write, so they get the umask default, usually `0644`.

`Cache::prune` has a second problem. When it cannot read the cache root it returns an empty list, exactly as it does when the root does not exist. The owner is sent to `mecha document prune` to clean up what other commands leave behind, so "removed 0" over a store the command could not read tells them it is clean when nothing was checked.

## What fixed looks like

- After any store through the cache (a layer or an OCR page), every directory from the cache root down to the file's own directory is `0700`. That includes a root that existed beforehand with looser permissions.
- Every stored file is `0600` from the moment it is created, temporary file included. It is never written at the umask default and tightened afterwards.
- If a directory cannot be made private, the store fails with an error. Callers already treat a failed store as a skipped cache write.
- `prune` on a missing root still succeeds and removes nothing. `prune` on a root that exists but cannot be read returns an error.
- Writes stay atomic: write to a temporary name beside the target, then rename into place.

Reuse the crate's existing owner-only directory helper.
