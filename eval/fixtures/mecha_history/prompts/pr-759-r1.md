# Harness rumination re-proposes a held setting at the next number

**Crates:** `mecha-core` (`src/harness.rs`, `src/diagnose.rs`), `mecha-cli` (`commands/harness.rs`, `commands/diagnose.rs`)

## Problem

The nightly diagnostician proposes `KEY=VALUE` changes over the closed `OverrideKey` set. Two places decide whether a proposal is new, `forbidding_prior` (CLI harness command) and the brief's `history_lines`, and both compare only the exact change. So while one value of a numeric setting is waiting on a person, or has been measured to do nothing, the loop can step the same setting through neighbouring values night after night.

## Desired behaviour

A record can **hold a setting**, which refuses every value of that setting, not just its own. A record holds a setting only when all of these are true:

- it is a `Config`-class record;
- its change parses;
- its verdict is staged, no observed effect, or owner no-effect;
- the setting is numeric (ordered). `effort` is categorical and is never held.

A record that was harmful, unmeasured, accepted or unparseable holds nothing.

**Which record is the holder.** Records are kept oldest first. For each setting, in `OverrideKey::ALL` order, the holder is the newest record that holds it. A hold is released by a later accepted or reverted `Config` record of the same setting whose change parses. Records that hold the setting after such a release still hold it.

**Naming the setting.** Read the setting a change names from its key alone, even when the value does not parse.

**Using the hold.** The check and the brief read this same predicate:

- `forbidding_prior` first returns any exact-change forbid, then the proposal's setting holder.
- `history_lines` never offers another value of a held setting as something that may be proposed again.
- `history_lines` keeps the holder in the brief past the newest-20 window.

**Messages.** Ruminate's "nothing new" message names the prior record's change and says whether this was a re-derivation or a held setting. The brief's staged and no-effect headings now also cover other values.

## Interface

In `mecha_core::harness`:

```rust
pub fn setting_of(change: &str) -> Option<OverrideKey>
pub fn setting_holders(on_file: &[HarnessCandidate]) -> Vec<&HarnessCandidate>
impl HarnessCandidate { pub fn held_setting(&self) -> Option<OverrideKey> }
```

In `mecha-cli`'s `commands::harness`, `forbidding_prior` keeps the signature it has now, which existing callers and tests use:

```rust
fn forbidding_prior<'a>(
    on_file: &'a [HarnessCandidate],
    change: &str,
    has_headroom: impl Fn(mecha_core::candidate::Metric) -> bool,
) -> Option<&'a HarnessCandidate>
```

In `mecha-cli`'s `commands::diagnose`, `history_lines` keeps the signature it has now:

```rust
pub fn history_lines(
    all: &[mecha_core::harness::HarnessCandidate],
    has_headroom: impl Fn(mecha_core::candidate::Metric) -> bool,
) -> Vec<mecha_core::diagnose::PastCandidate>
```
