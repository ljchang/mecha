# Record which features a run had on, and let an experiment environment require features

**Crate:** `mecha-core` (`src/session.rs`, `src/trial_env.rs`)

## Problem

A run's `RunConfig` records its levers but not which optional features were switched on. Some features change no tool names (`web`, `personas` and `voice`, for example), so the recorded tool list does not reveal them either. As a result, two experiment arms that differ only by a feature look identical, and a trial run with most features off looks the same in the record as a full one.

Experiment environments have a related gap. A task can need a feature that is off in the trial home. The trial runs anyway, and the failure is scored as though it were a real result.

## Desired behaviour

**Recording which features were on.**

- `RunConfig` gains an optional list of the features the run had switched on.
- `RunConfig::of` fills it with every feature that has a switch and is on according to `feature::switched_on`, in `Feature::ALL` order.
- An empty set is `Some(vec![])`.
- The field is serialized as an array of feature ids, and omitted from the JSON when it is `None`.
- Old records load the field as `None`.
- An id this build does not know makes the whole field `None`; never drop just that entry.

**Requiring features in an environment.**

- `environment.toml` accepts a `requires` list of feature ids, inherited down an `extends` chain.
- A `requires` entry that is not a feature id is refused when the environment loads. The error contains `` `<id>`, which is not a feature ``.
- After `Environment::prepare` builds the trial home's config, it refuses any required feature that is off or blocked there. The check reads binaries on `PATH`, never stores. The error names the environment and contains `` requires `<id>` ``.
- If `requires` is absent, nothing is checked.

## Interface

In `mecha_core::session`:

```rust
pub struct RunConfig {
    // ...existing fields...
    pub features_on: Option<Vec<crate::feature::Feature>>,
}
```
