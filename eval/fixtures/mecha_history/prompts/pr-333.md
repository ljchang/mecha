# The point-wise pass files owner-bound check points under the wrong reason

**Crate:** `mecha-cli` (`src/pointwise_pass.rs`, `src/probe.rs`)

## What is wrong

The point-wise comparison pass draws points from the corpus and drives them, counting every point it does not compare in `Tally` under the reason it was held back. A failed-check point is posed as an artifact probe, which executes its task, so `ProbePrep::unrunnable_under` refuses it unless hooks, the outbox and messages are all thrown off. The nightly runs with none of them off, by the owner's choice, so it never drives these points. That is expected, but it is reported badly in two ways:

- The refusal is counted as `unavailable`, the same number as "no such point could be prepared here". "None in the corpus" and "refused by this pass" call for opposite fixes, and they share a number.
- The refusal is asked only after the budget and seat checks. Once the budget is spent, every later owner-bound point is counted as `over_budget` (or `no_seat`), which reads as "raise the budget", a fix that changes nothing for them.

## What fixed looks like

**A refusal over the levers alone.** On `ProbePrep`, add a method that answers the same question as `unrunnable_under` from a list of thrown-off levers instead of a prepared run. `unrunnable_under` delegates to it with the prepared run's levers. It returns `None` for anything but an artifact probe, and otherwise names the first of hooks, outbox and messages that is not off, as today.

**A counter of its own.** `Tally` gains `owner_bound`, serialized beside the others. A point the levers refuse counts as owner-bound only when it is a `PointKind::FailedCheck` point; a refused point of any other kind counts as `unavailable`.

**The order of the gates.** Before a seat is taken or the run is prepared, the pass reads the levers it will run with, once per pass, from the same flags and config `setup::prepare` reads (`setup::levers_off`), and asks each posed point the lever question first. The gates then run in this order, and the first that holds a point back is the only one that counts it:

1. refused by the levers: `owner_bound` or `unavailable`, as above;
2. budget spent: `over_budget`;
3. no seat left: `no_seat`.

A point none of them holds back is driven, and counts under none of them. Keep the existing check against the prepared run after preparing, counted the same way, so a drift between the two fails closed.

**The readout.** The text summary's "skipped" line names owner-bound points apart from unavailable ones, as `<n> owner-bound, not driven`, placed after the unavailable count.

## Interface

In `mecha-cli`'s `src/probe.rs`:

```rust
impl ProbePrep {
    pub fn unrunnable_with(&self, levers_off: &[mecha_core::harness::Lever]) -> Option<String>
}
```

In `mecha-cli`'s `src/pointwise_pass.rs`:

```rust
pub struct Tally {
    // ...existing fields...
    pub owner_bound: usize,
}

/// Counts a refused point (owner_bound or unavailable) and returns `refused`.
fn count_unrunnable(tally: &mut Tally, kind: PointKind, refused: bool) -> bool

/// The three gates in order; true when the point is held back.
fn held_before_driving(
    tally: &mut Tally,
    kind: PointKind,
    refused: bool,
    budget: usize,
    seats_gone: bool,
) -> bool

/// The summary's "skipped: …" line.
fn skipped_line(t: &Tally) -> String
```
