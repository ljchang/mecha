# A delegated task's seed never tells the model to point its plan at that task

**Crate:** `mecha-cli` (`src/commands/tasks.rs`, `work_prompt` and `discuss_prompt`)

## What is wrong

When a board task is worked (`work_prompt`, a detached run) or discussed (`discuss_prompt`, a conversation with the owner), the seed prompt shows the task's id and tells the model to keep a `todo` list. The `todo` tool accepts a `serves` field, `"task:<id>"`, that records which goal the plan is for, and the run's goal is read from it. Its schema says to pass `serves` when work serves a task, but delegated runs still write their plans with no goal. The generic reminder never ties the instruction to this particular run's task.

`serves` is also replaced, never merged: each `todo` write rebuilds the plan from that call's input, and only the last write is read back. So a run that names the task on its first write and drops it later ends with no goal again.

## What fixed looks like

- `work_prompt`: when the task has a non-empty `id`, add a line to the seed telling the model to keep the `todo` list's `serves` field pointing at this task. It must pass `serves: "task:<id>"` with the task's actual id, using exactly that spelling, **every time you write it**. Say so in those words, so the plan and the board record agree.
- `discuss_prompt`: the same instruction, after its existing `todo` sentence. Use the task's actual id in `serves: "task:<id>"` and the words **every time you write the list**.
- When the task has no id, or an empty one, neither prompt gains the line.
- Nothing else in either prompt changes.

## Interface

In `mecha-cli`'s `src/commands/tasks.rs` (existing signatures, unchanged):

```rust
pub(crate) fn discuss_prompt(task: &Value, today: &str, reach: &Reach) -> String
fn work_prompt(task: &Value, today: &str, note: Option<&str>, unattended: bool, reach: &Reach) -> String
```
